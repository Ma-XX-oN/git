= Preload workers and generic manager

`git --preload-worker <session-directory>` starts a single-use Git process
that waits for one command. Set `PRELOAD_PID` to the native operating system
PID of the application that owns the session; on Windows also set
`PRELOAD_WIN_DIR` to the session's pipe directory. The worker creates
`worker-<pid>` inside the session directory before reporting READY. Its
channels are FIFOs in that directory on POSIX, and named pipes
`$PRELOAD_WIN_DIR\worker-<pid>\<channel>` on Windows.

== Generic preload library

=== Bash frontend

`preload/client/manager.sh` is a Bash library (Bash 4.1 or newer) for
preloading any executable that supports `--preload-worker`; Git is one such
executable. It must be sourced. Sourcing starts the session's native
`preload-manager` (`PRELOAD_MANAGER` selects an executable path or command;
the default is `preload-manager` on `PATH`) and defines `preload`. Sourcing
with `--python` runs the Python manager in `preload/manager/` instead, with
`PRELOAD_PYTHON` (default `python` on Windows, `python3` elsewhere):

----
source preload/client/manager.sh
preload git                 # or: preload /path/to/git
git status                  # served by a preloaded worker
command git status          # runs the executable directly
----

`preload <command>` starts three workers of `<command> --preload-worker`,
requiring each to report READY within one second; a program that does not
(including one that keeps running) is killed and rejected. It then defines and
exports a function named after the command's basename. The function inlines
the whole client, so a call costs no extra function indirection. Exported
functions reach child Bash processes; scripts run by `sh` use the executable.

=== PowerShell frontend

`preload/client/manager.ps1` is the PowerShell 7 frontend for Windows. Dot-source
it and start a session with the native paths of the worker and manager
executables, plus a new private session directory. Their runtime DLLs
must be on `PATH`. It uses the same native manager and worker protocol as Bash:

[source,powershell]
----
. ./preload/client/manager.ps1
Start-Preload -Executable C:/path/to/git.exe -Manager C:/path/to/preload-manager.exe `
    -Directory "$env:TEMP/preload-$([guid]::NewGuid())"
try {
    git status --short                       # the generated function streams
    $result = Invoke-Preload -Capture -Arguments @('status', '--short')
    $result.Stdout
    $result.Stderr
    $result.ExitCode
    $status = Invoke-Preload -Arguments @('--version') -DiscardOutput
} finally {
    Stop-Preload
}
----

`Start-Preload` registers one executable for the session and defines a
function named after it (`git.exe` becomes `git`); `Stop-Preload` removes the
function. The function calls `Invoke-Preload` with its arguments and any
pipeline input. `Invoke-Preload` accepts zero to 65535 parameters excluding the
executable name; empty and Unicode strings are preserved and embedded NULs are
rejected. Each invocation supplies the current filesystem directory. By
default it behaves like the native command: stdout lines go to the pipeline and
stderr lines to the error stream as they arrive, decoded with
`[Console]::OutputEncoding`; `$LASTEXITCODE` is set, and stderr never stops a
script even with `$ErrorActionPreference = 'Stop'`. There are no deadlines on a
running command, so long-running commands work. `-Capture` instead returns an
object with the full UTF-8 `Stdout` and `Stderr` and the `ExitCode`.
`-DiscardOutput` drains both streams to a null sink without buffering or
decoding and returns only the integer exit status.

Stdin is closed at once (the command reads EOF) unless input is supplied:
`-InputBytes` sends exact bytes (NULs included), `-InputPath` streams a file,
and `-InputLines` (what the function passes for pipeline input) sends lines
encoded with `$OutputEncoding`, as for native commands. Input is written while
output drains, then stdin is closed. `Start-Preload -Python` runs the Python
manager instead of `preload-manager`, with `$env:PRELOAD_PYTHON` or `python`
on `PATH`.

`git.exe` (the name with its extension) still runs the executable directly;
`& git` does not, because functions take precedence. Worker output is a pipe,
not a console, so Git disables color, the pager, progress and prompts as it
does for any non-terminal; Git aliases with `--color=always` can opt back into
color. The preloader itself knows nothing about the program it preloads.
Byte-exact native piping and redirection, `$PSNativeCommandUseErrorActionPreference`
and Ctrl+C handling are not yet equivalent to native commands. Workers inherit
the environment at manager startup. To refresh it, stop and start a session.
Manager log files remain in the supplied directory after shutdown.
Connecting to a pipe gives up after five seconds, and manager startup and the
`PRELOAD`/`STOP` control requests after fifteen; nothing else has a deadline.
The shared connector in `src/client/pipe.cs` is compiled once per PowerShell
process by the bundled `Add-Type` compiler; no separate C# build is required.

Call `Stop-Preload` in `finally`; repeated stop is allowed. Starting a second
session or dot-sourcing the client while its session is active throws without
discarding the existing session. After stopping, the client can be sourced again
and a new session started. Failed executable registration shuts down its manager.
The manager also watches its owning PowerShell process for termination.

=== Shared manager and transport

One manager serves every preloaded command. A pool starts with three workers,
starts one replacement per allocation, and grows by one worker (up to 32)
whenever a request has to wait for one. Replacements start only after the
reply that allocated a worker has been written, on a few long-lived spawner
threads, so starting a thread and a process never delays a reply. On
Linux/macOS each mailbox has its own long-lived thread that serves its
requests, so a request is handed to a waiting thread instead of starting one.
Setting `PRELOAD_TIMING` to a file makes calls record per-stage timestamps
and the manager log matching `TIMING` lines; `preload/perf/stage_timing.py`
reports them.

The Bash session directory is `preload-$PRELOAD_PID` under `$XDG_RUNTIME_DIR`
(Linux) or `$TMPDIR` (falling back to `/tmp`). It is created with mode 700 on
POSIX and must be owned by the current user. `PRELOAD_PID`, `PRELOAD_DIR` and,
on Windows, `PRELOAD_WIN_DIR` (`\\.\pipe\preload-$PRELOAD_PID`) are exported.
The sourcing shell owns the session; a separate child Bash process reuses it,
a subshell that sources the library gets its own session, and sourcing again
in the owning shell restarts the manager with the current environment and
re-registers its preloaded commands. The manager is not a job of the shell, so
a bare `wait` does not wait for it. Workers inherit the environment captured
when the manager starts; arguments and cwd are supplied per call.

Each call first obtains a worker from the manager. On both platforms the GET
reply is eight lowercase hexadecimal PID digits without a newline; a zero PID
(`00000000`) introduces an `ERROR <reason>` line, preserving allocation
diagnostics. The Bash client reads the frame with `read -r -N 8 -u` and
reconstructs the worker directory, `$PRELOAD_WIN_DIR\worker-<decimal-pid>` or
`$PRELOAD_DIR/worker-<decimal-pid>`. Bash reads a line from a pipe one byte
per `read()`, but a fixed-length frame in bulk.

* Windows: the client opens a new duplex connection to
  the session's `request` pipe for every call, sends `GET <name> <marker>` plus
  newline followed by the worker's argument/cwd request, and reads the PID frame
  from the same connection. It holds that connection until the call ends; see
  worker completion.
  The manager forwards the marker and request to the worker's `params-cwd`
  channel. The caller opens and marks only stdin, stdout, stderr and exit-code,
  then reads the worker's stdin ACK before writing or closing stdin.
  Each manager connection is a private reply channel, so concurrent callers
  never see each other's replies. Bash names the session pipe directory with
  `$PRELOAD_WIN_DIR`; PowerShell keeps a unique pipe name in its session state.
  The unmarked legacy `GET <name>` form is also accepted for clients that send
  their context directly to the worker.
* Linux/macOS: replies go through mailboxes, 32 FIFOs `slot.<n>` in the
  session directory. The client claims a free mailbox by creating
  `slot.<n>.lock` with Bash `noclobber` (an atomic exclusive create)
  containing its `$BASHPID`, opens `slot.<n>` for reading, writes
  `GET <name> <n>` plus newline to the `request` FIFO and blocks in `read` on
  the mailbox. The manager writes the PID frame into the mailbox, which wakes
  the client immediately: no polling, no CPU and no process while waiting. The client then sends `FREE <n>`; the manager drains the mailbox
  and deletes the lock. The manager holds both ends of every mailbox, so if
  it dies a waiting client's `read` returns end-of-file; a client checks the
  manager's PID before opening a mailbox, since that open would otherwise
  block without a writer. Locks whose `$BASHPID` has exited are reclaimed.
  The client keeps a never-read reader on the request FIFO so a write after
  the manager has exited cannot raise SIGPIPE. Signals cannot wake a client:
  Bash's `read` is not interrupted by a trapped signal (only `wait` is).

The other requests are `PRELOAD <name> <path>` (Linux/macOS:
`PRELOAD <name> <n> <path>`), which replies `OK` or `ERROR <reason>`,
on Linux/macOS `DONE <pid>` and `DONE <pid> <n> STATUS` (Windows uses the held
`GET` connection instead), described under worker completion, and
`STOP` (`STOP <n>`). On Linux/macOS the manager keeps serving after replying
to `STOP` until that caller's `FREE` arrives (at most five seconds), then
cleans up and exits. A worker whose reply cannot be delivered (the caller has
exited) is killed.

== Modules and ownership

`src/manager/` implements the generic C++17 manager as a separate executable.
It accepts `--owner-pid <native-pid>` and `--directory <existing-directory>`;
Windows also requires `--pipe-dir <named-pipe-directory>`. Arguments are UTF-8
internally, with native Unicode process/path APIs on Windows. Registration
selects each worker executable; the manager performs no Git initialization.

`src/worker/worker.c` owns dispatch, request framing, command execution and ordered
completion. `src/worker/worker-win32.c` and `src/worker/worker-posix.c` own native
endpoint setup, standard-handle adaptation and owner monitoring.
`src/worker/context.c` validates and applies the command's optional working
directory and environment changes. Workers inherit their environment when the
manager spawns them.

`include/shared/transport.h` exposes an opaque C transport. Start prepares endpoints
before READY, wait completes connection selection, and release cancels and
joins pending connection work before freeing storage. Configuration strings
are borrowed until release. A detached descriptor transfers ownership to the
caller; all other channels remain owned by the transport. Only the applicable
Windows or POSIX implementation is built. The unrelated index preloading
implementation is independent of these modules.
`include/shared/connection.h` supplies the common native connection operations
used by manager and worker. Public shared headers support both C and C++;
native handle/descriptor ownership transfers explicitly, and cancellation is
followed by joining I/O users before storage or endpoints are released.
POSIX worker mode requires pthread support for owner monitoring. Builds with
`NO_PTHREADS` retain ordinary Git commands and reject worker startup explicitly.

== Worker request and completion

Each worker exposes params-cwd, stdin, stdout, stderr and exit-code
channels and accepts connections in that order on both platforms: first the
request, which tells the worker what to run, then the standard streams in
descriptor order, then the status channel. The connection that writes the
request (the manager on Windows, the client on Linux/macOS) opens params-cwd;
the client opens the rest in order. A READY worker waits for its connections
with no time limit; owner death or the manager ends an idle worker. A failure
while connecting ends the worker with status 122 before the status channel
exists, so no `EXIT` record is written: the caller reports a connection
failure or, if its channels were already open, recovers the code as for a
worker that died mid-command.

The stdin channel is always the command's stdin; the worker never closes it.
The client either writes its input and then closes stdin, or closes it at once
so the command reads EOF; otherwise it closes when the worker process ends.
On Windows the worker writes one ACK byte (0x06) back on the duplex stdin pipe
once it has read every channel's marker. The client opens all its channels,
then waits for the ACK without a deadline before writing or closing stdin, so
closing cannot discard an unread marker. The read ends with the ACK, or with
EOF only if the worker process has ended; the status read then reports what
happened. POSIX FIFO opens already rendezvous, so there is no ACK there.
The Bash clients forward no caller input; the PowerShell client forwards
`-InputBytes` or `-InputPath`.

The context request begins with a little-endian 32-bit parameter count
excluding `git`, ranging from 0 to 65,535. It is followed by the NUL-terminated
UTF-8 executable name and then that many NUL-terminated UTF-8 parameters.
The worker allocates one argv entry for the executable, one per parameter,
and a terminating NULL pointer. Calls with more than 65,535 parameters return
255 with a diagnostic before requesting a worker. The worker also rejects
out-of-range wire counts. The separate 128 KiB request capacity still applies.
Client and worker must agree on this count convention. Historical benchmark
clients use a worker built from the same revision, selected with
`compare_dispatch.py --baseline-git`; the report records both worker
identities rather than claiming an unchanged-binary comparison.
The optional `cwd` field follows with its newline-terminated native path plus
NUL. Requests end with `end`
and NUL on both platforms; completion does not require closing the context
writer. The cwd newline lets the Bash client write `pwd` output directly
using a builtin. Remove exactly that last newline when decoding the path.
Argument count
and frame size are bounded by the worker.

Two more optional fields change the environment of one call. `env-del` holds
variable names and `env-add` holds `NAME=value` assignments, each entry ending
with a newline, for example `env-add` NUL `GIT_INDEX_FILE=x` LF `A=` LF NUL.
There is no escaping: names and values cannot contain a newline or NUL, a name
cannot be empty or contain `=`, and an assignment splits at its first `=`, so
values may contain `=`. An empty value sets the variable to the empty string,
unlike deletion. Fields may appear in any order, each at most once; an empty
field is allowed. The worker validates every field first, then changes the
working directory, deletes the `env-del` names and sets the `env-add`
assignments, so a name in both ends up set. Invalid fields end the worker with
status 128. Changes use Git's own `setenv`/`unsetenv`, so Git and the commands
it starts see them. Only the listed variables are sent, so the cost grows with
the changes, not with the environment: on the Windows laptop, replacing an
existing variable cost under 1 us and each new name about 22-32 us (see
`PERFORMANCE-JOURNAL.md`). The managers relay these fields unchanged; the Bash
and PowerShell clients do not send them.

All callers supply environment values when launching the manager. Replacement
workers inherit that same startup environment; changing it for every call
requires restarting the manager, and `env-del`/`env-add` change it for one
call. On Windows, launching the native manager from the owning Bash
runtime supplies the runtime's converted native environment directly.
The optional working directory and environment changes are applied before
ordinary Git initialization. On Windows, Git's startup code (before `main`)
derives a few variables such as `HOME`, `TMPDIR` and `LC_CTYPE` from the
manager's environment when they are unset; a per-call change does not redo
that derivation.

Completion flushes and closes stdout and stderr before writing `EXIT n` plus
newline on the status channel. Windows flushes the status pipe before closing
it, retaining the record until the client reads it. Clients drain both output
streams before reading status. Owner death terminates allocated as well as
idle workers; the manager also releases workers and allocation endpoints.

The manager retains every allocated worker until its call ends. A worker
that dies mid-command (a crash, or being killed) closes the status channel
without a record; the caller then asks for its status. The manager waits up
to ten seconds for that worker to exit, forgets it and replies `EXIT <code>`
with the raw process exit code (unsigned 32-bit on Windows),
`SIGNAL <number>` for a POSIX signal death, or `ERROR <reason>`.

* Linux/macOS: the caller ends every call with `DONE <pid>`, one line on the
  request FIFO with no reply. After a worker death it sends
  `DONE <pid> <n> STATUS` instead, which replies through mailbox `<n>`.
* Windows: the caller holds its `GET` connection for the whole call, and
  closing it ends the call. After a worker death it first sends a bare
  `STATUS` line on that connection. The manager scans the relayed worker
  request to its `end` field so that it relays nothing after it. Holding the
  connection measured about 0.15 ms per shell call faster than ending calls
  with a separate request on a new connection.

A POSIX caller killed mid-call never sends `DONE`, leaving one small record
until the manager exits; on Windows the OS closes the dead caller's
connection, which ends the call. The manager source records the
alternatives should this matter.

Each client reports what its shell reports for a direct run that ended the
same way:

* Bash on Linux/macOS returns 128 plus the signal number.
* Git Bash applies the MSYS mapping measured with MSYS2 Bash:
  `0xC0000005` (access violation) returns 139, `0xC000001D` (illegal
  instruction) 132, `0xC000013A` (Ctrl+C exit) 130, other codes from
  `0xC0000000` up 127, and lower codes their low eight bits.
* PowerShell sets `ExitCode` and `$LASTEXITCODE` to the code as a signed
  32-bit value, e.g. -1073741819 for an access violation.

Bash's own job message for a direct run, such as `Segmentation fault`, is not
reproduced. Output written before the worker died is delivered normally.

== Windows connection identification

Git Bash/MSYS2 opens make an additional connection that carries no
application marker: path resolution (`symlink_info::check()`) opens the pipe
before the real open (https://github.com/Ma-XX-oN/git/issues/7). Connection
arrival order does not identify the application connection, and a probe may
remain open, so closing state is not a reliable discriminator either.

Each logical Windows channel therefore has two pipe instances. The client
writes a marker immediately after opening the application connection. The
server consumes that byte before exposing application traffic. Pipe handles
are duplex even for application output channels, because the marker travels
from client to server. Worker names have the form
`$PRELOAD_WIN_DIR\worker-<pid>\<channel>`.

Two connector threads each handle one instance of every channel using
blocking ConnectNamedPipe and ReadFile calls. Their shared selection state
records the first marker and detects duplicate or invalid markers. The winner
cancels the other instance's pending operation with CancelIoEx and rendezvous
with its peer before either thread advances to the next channel. Cancellation
can race with submission, so cancellation retries until the peer has arrived
or cancellation has found pending I/O. Transport release waits for the
threads before destroying their shared state. Handles passed to the CRT stay
synchronous so Git's ordinary stream operations can use them directly.

Worker channels use the call's decimal marker; all five must agree. During
investigation, both candidate instances sometimes received characters. That
condition has stopped reproducing; the call-specific digit and duplicate
checks remain diagnostic safeguards, and errors report both received values.
The manager's request pipe needs no marker: every connection carries one
request, the throwaway connection closes without data and is disconnected,
and at least three instances are always listening so the real open never
finds the pipe busy.

POSIX FIFOs do not exhibit this Windows probe connection behavior. They use
ordinary directional FIFO opens in the agreed order, with no marker selection
or connector threads.

== Diagnostics and limits

`GIT_TRACE_PRELOAD` enables worker tracing. Startup, connection, malformed
request, marker, owner-death and cleanup failures are operational diagnostics.

The Bash client supports text output and commands that do not consume caller
stdin. Relaying arbitrary streams needs an executable with the available Bash
builtins; its process startup would undermine the speedup. A stream-copy builtin
is a proposed follow-up to enable forwarding without that startup cost.
The Bash clients close stdin right after connecting (after the Windows ACK),
so commands receive EOF on stdin. Bash variables cannot preserve embedded NUL
output, so arbitrary binary streams need a client that transfers bytes directly.

The Windows Bash client can hang when stderr fills its pipe buffer while the
client is waiting for stdout EOF. This includes large stderr-only responses and
commands that write to both streams. In the tested Git Bash runtime, the opened
Windows pipe descriptors are reported as regular files, so the client's 100 ms
`read` timeout does not interrupt the stdout read. Why this open path is not
reported as a special file has not been established. This pipe misclassification
causes the client to output stderr last, after stdout closes, even when stderr
bytes arrived earlier.
Newlines and writer-side flushes do not make that read switch to stderr.

The pipes request 64 KiB buffers, but this is not a fixed total-output limit or
a guaranteed safe stderr size. Large stdout-only responses can complete. The
failure depends on which stream the client is reading, when stdout closes and
how much unread stderr accumulates. Small stderr can fit in the buffer, letting
the command finish and close stdout so the client can switch to stderr. Larger
stderr can fill the buffer and block the command before it can close stdout,
while the client waits for that closure instead of draining stderr.
A full blocking pipe stalls its writer;
the observed failure is a deadlock, not discarded output. Use the ordinary Git
executable for commands that may generate substantial stderr. Native API
clients can drain both channels concurrently.

The client uses the platform's installed Bash. A builtin reader remains a
deferred follow-up.

== Validation and performance

Run `t/t5790-preload.sh` for normal regression integration and the scripts in
`preload/tests/` for native lifecycle, manager protocol, concurrency and serial
stress coverage (`test_manager.py` covers the request protocol, the
Windows throwaway connection, rejection of programs without READY and
concurrent calls).
`preload/tests/test_worker_crash.py` kills a worker mid-command (SIGSEGV, or
`STATUS_ACCESS_VIOLATION` on Windows) and requires the Bash client's status to
match a direct run, with the pool serving the next call.
`preload/tests/test_shell_output.py` checks small mixed output and large stdout-only
output on Windows. Its large stderr cases are opt-in diagnostics there, selected
with `--case stderr-large`, `--case out-first` or `--case err-first`; they may
time out under the documented limitation. POSIX acceptance runs all cases.
`t/perf/p5790-preload.sh` records paired direct and preloaded command timings.
Timing scripts require Bash 5.0 or newer for `EPOCHREALTIME`.
Development validation on Windows, Linux and macOS builds with Makefile and
Meson and exercises real workers, ownership/cleanup and 6,000 serial commands.
`preload/tests/test_existing_regressions.py` runs selected existing Git-file, alias
and configuration assertions through the `git` client function, preserving
their expected results and verifying actual worker allocations. Its case
selections cover the serial text-output contract. Excluded cases are not
reported as fast-path coverage.
The test adapter records each call from a Bash subshell; use the separate
paired benchmark for latency measurements. `preload/perf/compare_versions.py`
times two revisions' clients in alternating rounds on one runner, for example
this library against the earlier persistent-allocator client.

The complete ordinary-Git suites run only for final community-PR preparation,
after the final fast-path matrix succeeds. The acceptance workflow's manual
`community_pr` input enables that separate compatibility job; development pushes
leave it disabled. Investigative cleanup is followed by another fast-path run.

Record performance with matching client and manager versions, compiler
options, worker counts, workload and environment policy. Disable tracing
and investigative timing for measurements. Preserve raw samples, revisions
and machine details; compare revisions on the same machine.
