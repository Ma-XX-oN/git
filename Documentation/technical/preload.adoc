= Preloaded Git workers

`git --preload-worker <session-directory>` starts a single-use Git process
that waits for one command. Set `PRELOAD_PID` to the native operating system
PID of the application that owns the session; on Windows also set
`PRELOAD_WIN_DIR` to the session's pipe directory. The worker creates
`worker-<pid>` inside the session directory before reporting READY. Its
channels are FIFOs in that directory on POSIX, and named pipes
`$PRELOAD_WIN_DIR\worker-<pid>\<channel>` on Windows.

== Generic preload library

`contrib/preload/preload-manager.sh` is a Bash library (Bash 4.1 or newer) for
preloading any executable that supports `--preload-worker`; Git is one such
executable. It must be sourced. Sourcing starts the session's Python manager
(`PRELOAD_PYTHON` selects the interpreter; on Git Bash it must be native
Windows Python) and defines `preload`:

----
source contrib/preload/preload-manager.sh
preload git                 # or: preload /path/to/git
git status                  # served by a preloaded worker
command git status          # runs the executable directly
----

`preload <command>` starts three workers of `<command> --preload-worker`,
requiring each to report READY within one second; a program that does not
(including one that keeps running) is killed and rejected. It then defines and
exports a function named after the command's basename. The function inlines
the whole client, so a call costs no extra function indirection. Exported
functions reach child Bash processes; scripts run by `sh` use the executable.

One manager serves every preloaded command. A pool starts with three workers,
starts one replacement per allocation, and grows by one worker (up to 32)
whenever a request has to wait for one.

The session directory is `preload-$PRELOAD_PID` under `$XDG_RUNTIME_DIR`
(Linux) or `$TMPDIR` (falling back to `/tmp`). It is created with mode 700 on
POSIX and must be owned by the current user. `PRELOAD_PID`, `PRELOAD_DIR` and,
on Windows, `PRELOAD_WIN_DIR` (`\\.\pipe\preload-$PRELOAD_PID`) are exported.
The sourcing shell owns the session; a separate child Bash process reuses it,
a subshell that sources the library gets its own session, and sourcing again
in the owning shell restarts the manager with the current environment and
re-registers its preloaded commands. The manager is not a job of the shell, so
a bare `wait` does not wait for it. Workers inherit the environment captured
when the manager starts; arguments and cwd are supplied per call.

Each call first obtains a worker from the manager:

* Windows: the client opens a new duplex connection to
  `$PRELOAD_WIN_DIR\request` for every call, sends `GET <name>` plus newline and
  reads the worker's pipe directory from the same connection. Each connection
  is a private reply channel, so concurrent subshells never see each other's
  replies.
* Linux/macOS: the client writes `GET <name> <token>` plus newline to the
  `request` FIFO, where the token is `$BASHPID.<seq>` (a per-call counter).
  The manager writes the worker directory to a temporary file and renames it
  to `reply.<token>`; the client checks for that file in a loop, sleeping
  between checks in `read -t 0.0002` on the `bell` FIFO, which the manager
  holds open without writing, so waiting uses no CPU and no process. The
  client then sends `ACK <token>` and the manager deletes the file.
  `$BASHPID` (not `$$`) keeps replies private to each subshell, and the
  per-call counter keeps an earlier, not yet deleted reply from matching.
  Signals cannot wake the client: Bash's `read` is not interrupted by a
  trapped signal (only `wait` is).

The other requests are `PRELOAD <name> <path>` (Linux/macOS:
`PRELOAD <name> <token> <path>`), which replies `OK` or `ERROR <reason>`, and
`STOP` (`STOP <token>`). A worker whose reply cannot be delivered (the caller
has exited) is killed.

== Modules and ownership

`preload-worker.c` owns dispatch, request framing, command execution and ordered
completion. `preload-worker-win32.c` and `preload-worker-posix.c` own native
endpoint setup, standard-handle adaptation and owner monitoring.
`preload-context.c` validates and applies the command's optional working
directory. Workers inherit their environment when the manager spawns them.

`preload-transport.h` exposes an opaque transport. Start prepares endpoints
before READY, wait completes connection selection, and release cancels and
joins pending connection work before freeing storage. Configuration strings
are borrowed until release. A detached descriptor transfers ownership to the
caller; all other channels remain owned by the transport. Only the applicable
Windows or POSIX implementation is built. The unrelated index preloading
implementation is independent of these modules.
POSIX worker mode requires pthread support for owner monitoring. Builds with
`NO_PTHREADS` retain ordinary Git commands and reject worker startup explicitly.

== Worker request and completion

Each worker exposes stdin, stdout, stderr, exit-code and params-cwd
channels. The client opens stdout, stderr, status, stdin and context in that
order. The context request begins with a little-endian 32-bit argument count
including `git`, followed by that many NUL-terminated UTF-8 arguments.
The optional `cwd` field follows with its newline-terminated native path plus
NUL. Requests end with `end`
and NUL on both platforms; completion does not require closing the context
writer. The cwd newline lets the Bash client write `pwd` output directly
using a builtin. Remove exactly that last newline when decoding the path.
Argument count
and frame size are bounded by the worker.

All callers supply environment values when launching the manager. Replacement
workers inherit that same startup environment; updating it requires restarting
the manager. On Windows, launching the native manager from the owning Bash
runtime supplies the runtime's converted native environment directly.
The optional working directory is applied before ordinary Git initialization.

Completion flushes and closes stdout and stderr before writing `EXIT n` plus
newline on the status channel. Windows flushes the status pipe before closing
it, retaining the record until the client reads it. Clients drain both output
streams before reading status. Owner death terminates allocated as well as
idle workers; the manager also releases workers and allocation endpoints.

== Windows connection identification

Git Bash/MSYS2 opens make an additional connection that carries no
application marker: path resolution (`symlink_info::check()`) opens the pipe
before the real open (https://github.com/Ma-XX-oN/git/issues/7). Connection
arrival order does not identify the application connection, and a probe may
remain open, so closing state is not a reliable discriminator either.

Each logical Windows channel therefore has two pipe instances. The client
writes a marker immediately after opening the application connection. The
server consumes that byte before exposing application traffic. Pipe handles
are duplex even for application output channels, because the marker travels
from client to server. Worker names have the form
`$PRELOAD_WIN_DIR\worker-<pid>\<channel>`.

Two connector threads each handle one instance of every channel using
blocking ConnectNamedPipe and ReadFile calls. Their shared selection state
records the first marker and detects duplicate or invalid markers. The winner
cancels the other instance's pending operation with CancelIoEx and rendezvous
with its peer before either thread advances to the next channel. Cancellation
can race with submission, so cancellation retries until the peer has arrived
or cancellation has found pending I/O. Transport release waits for the
threads before destroying their shared state. Handles passed to the CRT stay
synchronous so Git's ordinary stream operations can use them directly.

Worker channels use the call's decimal marker; all five must agree. During
investigation, both candidate instances sometimes received characters. That
condition has stopped reproducing; the call-specific digit and duplicate
checks remain diagnostic safeguards, and errors report both received values.
The manager's request pipe needs no marker: every connection carries one
request, the throwaway connection closes without data and is disconnected,
and at least three instances are always listening so the real open never
finds the pipe busy.

POSIX FIFOs do not exhibit this Windows probe connection behavior. They use
ordinary directional FIFO opens in the agreed order, with no marker selection
or connector threads.

== Diagnostics and limits

`GIT_TRACE_PRELOAD` enables worker tracing. Startup, connection, malformed
request, marker, owner-death and cleanup failures are operational diagnostics.

The Bash client supports text output and commands that do not consume caller
stdin. Relaying arbitrary streams needs an executable with the available Bash
builtins; its process startup would undermine the speedup. A stream-copy builtin
is a proposed follow-up to enable forwarding without that startup cost.
Workers receive EOF on stdin. Bash variables cannot preserve embedded NUL
output, so arbitrary binary streams need a client that transfers bytes directly.

The Windows Bash client can hang when stderr fills its pipe buffer while the
client is waiting for stdout EOF. This includes large stderr-only responses and
commands that write to both streams. In the tested Git Bash runtime, the opened
Windows pipe descriptors are reported as regular files, so the client's 100 ms
`read` timeout does not interrupt the stdout read. Why this open path is not
reported as a special file has not been established. This pipe misclassification
causes the client to output stderr last, after stdout closes, even when stderr
bytes arrived earlier.
Newlines and writer-side flushes do not make that read switch to stderr.

The pipes request 64 KiB buffers, but this is not a fixed total-output limit or
a guaranteed safe stderr size. Large stdout-only responses can complete. The
failure depends on which stream the client is reading, when stdout closes and
how much unread stderr accumulates. Small stderr can fit in the buffer, letting
the command finish and close stdout so the client can switch to stderr. Larger
stderr can fill the buffer and block the command before it can close stdout,
while the client waits for that closure instead of draining stderr.
A full blocking pipe stalls its writer;
the observed failure is a deadlock, not discarded output. Use the ordinary Git
executable for commands that may generate substantial stderr. Native API
clients can drain both channels concurrently.

The client uses the platform's installed Bash. A builtin reader remains a
deferred follow-up.

== Validation and performance

Run `t/t5790-preload.sh` for normal regression integration and the scripts in
`t/preload/` for native lifecycle, manager protocol, concurrency and serial
stress coverage (`test_preload_manager.py` covers the request protocol, the
Windows throwaway connection, rejection of programs without READY and
concurrent calls).
`t/preload/test_shell_output.py` checks small mixed output and large stdout-only
output on Windows. Its large stderr cases are opt-in diagnostics there, selected
with `--case stderr-large`, `--case out-first` or `--case err-first`; they may
time out under the documented limitation. POSIX acceptance runs all cases.
`t/perf/p5790-preload.sh` records paired direct and preloaded command timings.
Timing scripts require Bash 5.0 or newer for `EPOCHREALTIME`.
Development validation on Windows, Linux and macOS builds with Makefile and
Meson and exercises real workers, ownership/cleanup and 6,000 serial commands.
`t/preload/test_existing_regressions.py` runs selected existing Git-file, alias
and configuration assertions through the `git` client function, preserving
their expected results and verifying actual worker allocations. Its case
selections cover the serial text-output contract. Excluded cases are not
reported as fast-path coverage.
The test adapter records each call from a Bash subshell; use the separate
paired benchmark for latency measurements. `t/perf/compare_preload_versions.py`
times two revisions' clients in alternating rounds on one runner, for example
this library against the earlier persistent-allocator client.

The complete ordinary-Git suites run only for final community-PR preparation,
after the final fast-path matrix succeeds. The acceptance workflow's manual
`community_pr` input enables that separate compatibility job; development pushes
leave it disabled. Investigative cleanup is followed by another fast-path run.

Record performance with matching client and manager versions, compiler
options, worker counts, workload and environment policy. Disable tracing
and investigative timing for measurements. Preserve raw samples, revisions
and machine details; compare revisions on the same machine.
