Preinitialized Git worker (experimental)
=========================================

This document describes the native `git --preload` worker process contract.
It is not the ordinary Git CLI interface. The initial upstream proposal
must separately demonstrate binary, error, timeout and security acceptance
before this behavior can be called production-ready.

Launch and ownership
--------------------

On Windows, the only valid invocation is `git --preload`, with no additional
options, commands or positional arguments. On Linux/macOS the existing Unix
manager launches `git --preload <private-worker-directory>`, which contains
its precreated 0600 FIFOs. In particular,
`git -C DIR --preload`, `git --preload status` and
`git --preload --workers 4` fail with exit status 129 without starting
a worker. The external manager configures the worker count and lifecycle;
`--preload` starts exactly one worker.

`git --preload` (no other arguments) starts a *single-use* native Git
worker. It writes `READY <native-win32-pid>\n` to the original launcher
stdout after creating four native Windows named pipes, then waits for a
command request. A separate shell-owned manager starts several workers,
collects READY messages, returns an available worker's PID to its caller
and immediately starts preparing a replacement. The manager only
allocates workers; it does **not** forward Git arguments, stdout, stderr
or exit status.

Four direct worker channels
---------------------------

For PID `12345` the endpoints are:

* `\\\\.\\pipe\\12345-stdin`: client writes one argument frame;
* `\\\\.\\pipe\\12345-stdout`: worker writes stdout bytes;
* `\\\\.\\pipe\\12345-stderr`: worker writes stderr bytes;
* `\\\\.\\pipe\\12345-exit-code`: worker writes its final status.

The Git for Windows Bash implementation uses two native pipe instances
for each *logical* endpoint. This is an interoperability workaround for
the extra Bash connection established before the data-bearing handle,
not a separate read/write channel. The worker accepts its channels in
the order stdout, stderr, exit-code, stdin. Pipe names are process-PID
scoped; the manager's allocation pipe is a fifth logical channel.

The stdin frame consists of a little-endian uint32 argument count
(including the leading `git` string), then the count's NUL-terminated
UTF-8 byte strings concatenated without padding. The frame must contain
1..32 strings, be no more than 4096 bytes total, and name `git` as its
first string. The worker rejects malformed lengths and malformed UTF-8.
This `stdin` endpoint currently carries a command *frame*, not streamed
standard input. When the request writer closes, the worker installs the
remaining readable endpoint as Git's stdin (EOF after draining). Full
interactive/piped stdin forwarding remains outstanding.

The worker executes Git once. stdout and stderr are raw byte streams
without framing and are required to preserve bytes including embedded
NUL. Each stream has its own pipe so they can be drained concurrently.
After Git execution, the worker flushes and closes both streams. Only
then does it send the ASCII status record `EXIT <decimal-code>\n` on the
exit-code channel. Consumers must drain stdout and stderr to EOF before
using the exit-code channel, and must not confuse empty-but-open with EOF.

The Bash `git-ipc` experimental client uses `read -d ''` with a 100 ms
timeout for text workloads and has no binary-output guarantee. Binary
parity must be exercised using a native client that preserves bytes
rather than Bash variables. The original Git process's native status is
returned for successfully completed commands; the Bash IPC wrapper
returns 255 and prints `GIT-IPC ERROR: ...` on a transport failure.

Request context, scope and lifecycle
-----------------------------------

Ordinary `git <command>` and every non-`--preload` invocation must stay
unchanged on all operating systems. The permanent Unix worker now uses four
private FIFOs, and Windows uses native Win32 named pipes. The Bash managers
allocate a single-use worker and do not relay command bytes.

A request is a little-endian argument count and its NUL-separated UTF-8
arguments, optionally followed by tagged fields: `cwd\0<UTF-8-directory>\0`
and `env\0<uint32-length><NUL-separated-UTF-8-environment-block>`.
The latter is a complete effective environment snapshot. The worker applies
both before Git command initialization, and terminates after that one command;
the caller's environment remains unchanged. Native acceptance for these fields
is pending. Interactive/piped stdin forwarding, general terminal usage,
concurrent requests to the same worker, arbitrary signals and cancellation,
and full Git command parity remain outstanding.

Security and recovery acceptance remains mandatory. Production use
requires verifying access control for PID-addressed pipes, ownership
validation, client disconnect/abandoned-output time limits, stale
workers, owner exit and cancellation; an open pipe alone is not proof
that the caller is authorized. On ordinary worker exit Windows releases
kernel pipe handles, but an unresponsive worker must be terminated by
its owning manager. The shell manager's temporary ready/log directory
has separate lifecycle cleanup requirements.

Native acceptance checks
------------------------

Native CI must compile this *normal source checkout* without
the temporary `GIT809_WORKER_PROBE` instrumentation, test the READY/PID
handshake, four pipe channels, framing and statuses, compare stdout,
stderr and status against direct Git (including NUL-containing binary
data, Unicode and nonzero exits), test slow readers/EOF and timeout
failure paths, test worker replacement and normal Git compatibility,
then benchmark at least 100 paired operations. CI results are valid
only for the precise source commit and configuration tested.
